# Interface languages

Tabs already contained `js/i18n.js` and a copy of the Simple dictionary, but its
language controls displayed a warning and much of its markup and table schema
used literal German labels. Tabs now uses the existing runtime throughout its
interface, with a single fetch of its local `data/i18n.json` before boot.

## Behaviour

- Supported languages: German (`de`), French (`fr`), Italian (`it`), English (`en`).
- `?lang=` selects the initial language. Missing or unsupported languages default
  to German. Language changes update the URL with `replaceState`, the HTML language
  and both desktop and phone controls; no reload or data fetch is needed.
- Static labels, hints and accessibility labels use `data-i18n` attributes.
  Mixed icon/text buttons bind only their text span, so translating never removes
  the icon. Table schemas use `labelKey` and the table's existing language hook.
- Generated info labels, gallery labels, location tree, search suggestions,
  detail fallbacks, export counts and image/document preview controls translate.
  A language change dismisses and cancels pending search results in the old
  language. Subsequent external searches use the selected language.
- A language change does not reload the selected building, reset its tables,
  change the carousel image or move the map. Responsive address labels translate
  along with their column headings.
- Record values (names, addresses, classifications, measurement sources), photo
  descriptions/credits and document bodies remain in their source language.
  Swagger UI/specification and third-party map attribution keep their own text.
  This is interface localization, not a translation of source records.

## Maintaining translations

Each key has `de`, `en`, `fr` and `it` strings. Include the same named placeholders
in every language, for example `{count}`. Use complete sentence templates rather
than joining translated word fragments. Dynamic data inserted into HTML must
still be escaped after interpolation.

Use `t('key', params)` at render time, not when modules are first imported: the
dictionary has not loaded at import time. For persistent dynamic UI, use a
`data-i18n` binding or register one `onLangChange` callback during initialization.
Avoid registering callbacks every time a view opens.

Both prototypes remain independent: runtime imports and dictionaries are local.
The expanded dictionaries and localized versions of the pre-existing table,
carousel, mini-map and media-viewer modules are maintained as separate aligned
copies. There is no new shared runtime module or cross-prototype import.

## Verification

From the repository root:

```sh
node test/run.js test/scenarios/tabs-i18n.js
node test/all.js
node test/check-alignment.js
node test/check-independence.js
```

The localization scenario checks all dictionary languages and parameters, markup
keys, deep links, both selectors, all entity table headers, selection/filter/sort
preservation, previews, search templates, escaping and fallback behaviour.

With a static server on port 8123, `node test/i18n-visual.js` checks desktop and
phone layouts for all four languages across map, gallery and detail views. It
also verifies the permanently underlined address link and unlined location icon
in both prototypes. Screenshots and results are written to `tmp/i18n-visual`.
